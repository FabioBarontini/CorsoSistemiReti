PROTOCOLLI

Il giorno in cui il Web imparò a parlare.

Una richiesta attraversa la rete. Un server ascolta. Poi risponde.

01 · LA DOMANDA

Non basta avere una pagina.

Un documento può esistere su una macchina lontana. Ma come si fa a chiederlo? E come fa quella macchina a capire cosa vogliamo?

Il Web ha bisogno di un linguaggio comune. Non un linguaggio umano. Un protocollo.

«Chiedimi una risorsa. Io saprò cosa significa la tua richiesta. E saprò come risponderti.»
02 · HTTP

Richiesta. Risposta.

HTTP, HyperText Transfer Protocol, definisce il modo in cui client e server si scambiano messaggi per trasferire risorse sul Web.

Il client invia una richiesta. Il server la interpreta e restituisce una risposta. Dentro quei messaggi ci sono metodi, intestazioni, codici di stato e, quando serve, un corpo.

GET

Chiedi

Recuperare una rappresentazione di una risorsa.

POST

Invia

Inviare dati al server per creare o elaborare qualcosa.

404

Non trovato

Il server ha ricevuto la richiesta, ma non trova la risorsa richiesta.

200

OK

La richiesta è stata gestita con successo.

301

Spostato

La risorsa ha un nuovo indirizzo.

500

Errore server

Qualcosa non ha funzionato nell'elaborazione lato server.

03 · DALLA STORIA ALLA TECNICA

Il Web diventa una conversazione.

Quando apri una pagina oggi, quella semplicità nasconde una lunga storia di standardizzazione. URL indica dove cercare; HTTP definisce come chiedere e rispondere; HTML descrive una struttura ipertestuale; il browser traduce tutto questo in un'esperienza visiva.

Da qui nascerà un altro passaggio: le macchine non si limiteranno a scambiarsi documenti. Cominceranno a scambiarsi dati. E il Web diventerà un modo per costruire applicazioni.

04 · UNA RICHIESTA REALE

Il browser non “mostra” una pagina. La chiede.

Quando digiti un indirizzo, il browser deve prima sapere dove trovare il server. Poi deve aprire una connessione e formulare una richiesta comprensibile al servizio remoto.

Una richiesta HTTP può contenere un metodo come GET, un percorso come /index.html e intestazioni che descrivono il contesto della richiesta. Il server costruisce una risposta con uno status code, intestazioni e, se necessario, un corpo.

Quello che vediamo come una pagina è quindi il risultato finale di una conversazione strutturata.

Dietro un clic c’è una frase che una macchina sa leggere.
CAPITOLO · HTTP

Una pagina Web non appare: viene chiesta

Il browser sembra una finestra. In realtà è un interlocutore. Quando scrivi un indirizzo e premi Invio, non stai semplicemente 'aprendo una pagina': stai avviando una sequenza di comunicazioni. Prima bisogna capire dove si trova il server, poi stabilire una comunicazione, poi formulare una richiesta secondo un linguaggio che il server sappia interpretare.

HTTP nasce come protocollo per trasferire risorse ipertestuali. Il verbo GET è quasi una frase: dammi questa risorsa. Il server risponde con una struttura che contiene almeno uno stato e, quando necessario, il contenuto richiesto. Il celebre 200 OK è diventato un simbolo proprio perché racconta una cosa molto semplice: la richiesta è stata capita e la risposta può essere consegnata.

I codici di stato costruiscono una piccola grammatica narrativa della rete. 404 racconta che la risorsa non è stata trovata; 301 e 302 raccontano una redirezione; 500 racconta un errore interno. Sono numeri, ma possono essere letti come battute di dialogo tra client e server.

La cosa più sorprendente è quanto poco il browser debba sapere del contenuto prima di chiederlo. Conosce il protocollo, la risorsa e il server. Il resto emerge dalla risposta. Il Web è quindi un sistema di richieste e risposte che diventa visibile solo quando qualcosa si rompe: quando appare un 404, finalmente ci accorgiamo che dietro la pagina c'era una conversazione.

NOTA A MARGINECURIOSITÀ · HTTP è un protocollo applicativo: il suo compito non è trasportare direttamente i segnali sul filo, ma definire la conversazione tra applicazioni Web.
