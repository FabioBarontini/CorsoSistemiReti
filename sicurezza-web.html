MAPPA DELLA LEZIONE 02
CAPITOLO 06 · WEB SECURITY

Il browser non sa se ciò che riceve è fidato.

Quasi tutti gli attacchi alle applicazioni condividono una radice: il programma si fida troppo dell'input. SQL injection, XSS, CSRF, IDOR, path traversal, command injection, buffer overflow e deserializzazione insicura sono modi diversi di trasformare dati in qualcosa che il programma non avrebbe dovuto eseguire o mostrare.

La regola d'oro dello sviluppo sicuro è semplice da dire e difficile da applicare: non fidarti mai dell'input.
SQL INJECTION01

Quando il dato entra nel posto sbagliato.

Immaginiamo un login costruito concatenando direttamente ciò che l'utente scrive: SELECT * FROM utenti WHERE username = '<input>' AND password = '<input>';. Se il programma tratta l'input come parte del codice SQL invece che come semplice dato, un input manipolato può cambiare la logica della query. Un esempio didattico classico mostra come una condizione inserita nell’input possa alterare la logica della query e commentare il resto dell’istruzione.

ERRORE

Concatenare direttamente input non fidato nella query.

DIFESA

Prepared statements, validazione dell'input e account database con privilegi minimi.

Nel 2008 una SQL injection contribuì al furto di dati di circa 130 milioni di carte di credito da Heartland Payment Systems; nel 2015 TalkTalk subì una violazione che coinvolse circa 157.000 clienti.

XSS02

Quando il commento di qualcuno diventa codice nel browser di qualcun altro.

Nel Cross-Site Scripting, un attaccante riesce a far eseguire JavaScript nel browser della vittima. Può essere stored, reflected o DOM-based. Il caso Samy su MySpace nel 2005 trasformò una vulnerabilità XSS in un worm che si propagava visitando profili.

Il problema non è che JavaScript sia pericoloso. Il problema è farlo eseguire nel contesto sbagliato.

La difesa passa dall'escaping dell'output, Content Security Policy e cookie HttpOnly. L'obiettivo è impedire che dati trattati come testo vengano interpretati come istruzioni.

ALTRE PORTE03

Una pagina Web può aprire molte più porte di quanto sembri.

CSRF

Un sito malevolo induce il browser autenticato a compiere una richiesta verso un altro sito. Token anti-CSRF e cookie SameSite sono contromisure.

IDOR

Cambiare un identificatore nell'URL non dovrebbe permettere di vedere la risorsa di un altro utente. I permessi vanno verificati sul server a ogni richiesta.

PATH TRAVERSAL

Sequenze come ../ possono tentare di uscire dalla directory prevista. Validare i percorsi e usare il privilegio minimo.

COMMAND INJECTION

L'input finisce in un comando del sistema operativo. Meglio evitare la shell quando non serve e validare strettamente i dati.

BUFFER OVERFLOW

Scrivere oltre i limiti di un'area di memoria può sovrascrivere dati e controllo del programma.

DESERIALIZZAZIONE / RCE

Dati manipolati possono trasformarsi in esecuzione di codice remoto. Aggiornare librerie e non deserializzare dati non fidati.

Questi casi, insieme agli errori di controllo accessi e agli errori crittografici, rientrano nel territorio affrontato dall'OWASP Top 10.

HEARTBLEED04

La vulnerabilità che faceva perdere pezzi di memoria.

Heartbleed, nel 2014, colpì OpenSSL. Un bug permetteva a una richiesta malformata di ottenere dati dalla memoria del processo del server. Il caso è diventato un simbolo perché il software che proteggeva una parte enorme del Web dipendeva da una comunità di manutentori molto piccola.

Log4Shell, nel 2021, mostrò un altro tipo di fragilità: una libreria Java usata in milioni di applicazioni, con una vulnerabilità valutata CVSS 10/10. Le chat di Minecraft furono tra i luoghi in cui circolarono rapidamente le prime prove.

La lezione è più grande della singola vulnerabilità: la sicurezza del Web dipende anche da software che spesso non vediamo.

VULNERABILITÀ05

Il Web ha anche una memoria degli errori.

Ogni vulnerabilità pubblicamente riconosciuta può ricevere un identificativo CVE. Il punteggio CVSS, da 0 a 10, descrive la gravità. Gli strumenti di vulnerability assessment confrontano le versioni installate con questi archivi per individuare ciò che deve essere corretto.

Heartbleed è CVE-2014-0160. Il caso mostra anche un problema organizzativo: OpenSSL, componente critico usato da una parte enorme dell'infrastruttura Web, era mantenuto da un numero molto ridotto di volontari.

CASI06

Due numeri, due lezioni.

Nel 2008 Albert Gonzalez sfruttò una SQL injection per sottrarre dati relativi a circa 130 milioni di carte di credito da Heartland Payment Systems. Nel 2015 TalkTalk subì una violazione che coinvolse circa 157.000 clienti; tra gli autori c'erano ragazzi di 15 e 16 anni.

Nel 2005 il worm Samy sfruttò una XSS di MySpace: chi visitava il profilo di Samy Kamkar lo aggiungeva come amico e copiava il codice nel proprio profilo. In circa venti ore oltre un milione di utenti risultarono coinvolti.
