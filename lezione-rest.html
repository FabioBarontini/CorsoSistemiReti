API · REST

Il Web impara a parlare con le macchine.

Non chiedere più una pagina. Chiedi una risorsa. Trasformare il Web in un linguaggio per applicazioni.

01 · IL CAMBIAMENTO

Prima c'erano documenti.

Il Web nasce attorno a documenti collegati. Ma le applicazioni crescono. Hanno bisogno di dati: studenti, prodotti, messaggi, ordini, fotografie.

La domanda cambia: come possiamo chiedere dati a un sistema remoto usando lo stesso linguaggio del Web?

02 · REST

Le risorse entrano in scena.

Nel modello REST l'idea centrale è trattare ciò che un sistema espone come risorse identificabili. Il client non deve conoscere la struttura interna del server: interagisce attraverso un'interfaccia uniforme.

GET /studenti/42
POST /studenti
PUT /studenti/42
DELETE /studenti/42
RESOURCE

Una cosa.

Uno studente, un libro, un prodotto, una foto possono essere trattati come risorse.

URI

Un'identità.

Una risorsa deve poter essere identificata.

STATELESS

Niente memoria implicita.

Ogni richiesta contiene le informazioni necessarie per essere interpretata.

JSON

Dati.

Una rappresentazione leggera e molto usata per trasportare strutture dati.

03 · CRUD

Quattro verbi, un mondo.

Creare, leggere, modificare, eliminare. Il modello CRUD si incontra naturalmente con i metodi HTTP e rende evidente come il Web possa diventare un'interfaccia per applicazioni.

04 · FIELDING

REST non è un pulsante. È un modo di pensare.

Roy Fielding non inventa un “protocollo REST”. Analizza le caratteristiche che rendono il Web evolvibile e descrive un insieme di vincoli architetturali.

La separazione tra client e server, la statelessness, la cache, l’interfaccia uniforme e la possibilità di introdurre intermediari sono parte di questa architettura.

Quando oggi chiamiamo una API REST, stiamo usando un linguaggio nato dall’osservazione del Web come sistema distribuito.

La domanda di Fielding non è “come faccio una API?”. È “quali proprietà rendono il Web capace di crescere?”.
CAPITOLO · ROY FIELDING

L'architetto invisibile che prova a capire perché il Web funziona

Roy Fielding entra nella storia in un momento in cui il Web è già diventato un luogo complesso. La domanda non è più soltanto come trasferire una pagina, ma come progettare sistemi che possano comunicare con il Web senza essere incatenati a una singola implementazione.

La sua ricerca aiuta a formalizzare un insieme di principi architetturali che diventeranno noti attraverso il termine REST. Il punto importante è che REST non nasce come un linguaggio da imparare a memoria, ma come un modo di descrivere perché certe proprietà rendono il Web scalabile e interoperabile.

Risorse identificabili, rappresentazioni, interazioni stateless, cache, interfaccia uniforme: dietro parole apparentemente astratte c'è una preoccupazione concreta. Se milioni di client devono parlare con migliaia di server, non possiamo progettare ogni conversazione come un accordo privato tra due programmi. Servono convenzioni abbastanza generali da permettere a sistemi diversi di incontrarsi.

Il paradosso è che Fielding lavora su qualcosa che l'utente non vede. Quando REST funziona bene, la persona vede semplicemente una pagina o un'applicazione che risponde. L'architettura è invisibile. Ed è proprio questa invisibilità a renderla interessante: una buona architettura fa sembrare naturale ciò che, sotto, richiede molte regole.

NOTA A MARGINECURIOSITÀ · REST è spesso confuso con 'API HTTP'. In realtà è un insieme di vincoli architetturali; un'API può usare HTTP senza essere necessariamente RESTful.

APPROFONDIMENTO · REST

QUANDO UN PROTOCOLLO DIVENTA UN LINGUAGGIO

REST viene spesso ridotto a una lista di parole: GET, POST, PUT, DELETE. Ma la storia è più interessante. Fielding osserva il Web e cerca di descrivere quali proprietà architetturali gli permettono di funzionare su scala enorme.

Una risorsa non è semplicemente un file. È qualcosa che può essere identificato e rappresentato. Il client non deve possedere tutta la logica interna del server; deve conoscere le regole dell'interfaccia. Questa separazione permette ai sistemi di evolvere senza richiedere che ogni parte conosca l'implementazione delle altre.

La grande lezione di REST è quindi una lezione di progettazione: non costruire una conversazione privata quando puoi costruire una convenzione generale. Più la convenzione è stabile, più sistemi diversi possono partecipare allo stesso ecosistema.
